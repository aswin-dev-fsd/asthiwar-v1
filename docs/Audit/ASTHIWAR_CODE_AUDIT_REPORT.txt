BUG-03 — Volume Rate Detection Uses Wrong Type Lookup (Always Multiplier=2)
--------------------------------------------------------------------------------
Severity : CRITICAL
File     : frontend/src/components/calculator/Step3Packages.tsx
Impact   : Volume discount badge on all package cards is always computed with
           multiplier=2, regardless of actual floor count. Wrong pricing info
           shown to every user for every configuration.

ROOT CAUSE
formData.floorCount is always a NUMBER (0, 1, 2, 3). The floorMultipliers object
has STRING keys ("Ground", "G+1", etc.). Looking up a number key in a
string-keyed Record returns undefined, so the || 2 fallback always fires.

BROKEN CODE:
  const floorMultipliers: Record<string, number> = {
    Ground: 1, 'G+1': 2, 'G+2': 3, 'G+3': 4
  };
  const multiplier = floorMultipliers[formData.floorCount] || 2;
  // formData.floorCount = 0 (number) → floorMultipliers[0] = undefined → 2

FIX (derive from the number directly):
  const multiplier = (formData.floorCount || 0) + 1;
  // floorCount=0 → 1, floorCount=1 → 2, floorCount=3 → 4

BUG-04 — updateAdminOptionPrice() Drops packageId and priceType
--------------------------------------------------------------------------------
Severity : CRITICAL
File     : backend/src/modules/admin/admin-config.service.ts
           (updateAdminOptionPrice function)
Impact   : Any admin price update on a package-specific option creates a new
           version that applies universally to ALL packages. Pricing tier
           separation is permanently destroyed for that option.

ROOT CAUSE
The INSERT for the new price version is missing packageId (defaults to NULL =
universal) and priceType (defaults to schema default 'per_sqft', cannot
preserve 'fixed' type options). The old row gets effectiveTo=now, so the
package-specific scoping is permanently lost.

BROKEN CODE:
  const [newPrice] = await db.insert(schema.optionPrices).values({
    optionId,
    priceDelta: dto.priceDelta.toFixed(2),
    effectiveFrom: now,
    effectiveTo: null,
    // packageId: MISSING → NULL → becomes universal price
    // priceType: MISSING → schema default 'per_sqft'
  }).returning();

FIX (fetch the existing row first, carry forward packageId and priceType):
  const existingPrice = await db.query.optionPrices.findFirst({
    where: and(
      eq(schema.optionPrices.optionId, optionId),
      isNull(schema.optionPrices.effectiveTo)
    ),
  });
  const [newPrice] = await db.insert(schema.optionPrices).values({
    optionId,
    packageId: existingPrice?.packageId ?? null,       ← carry forward
    priceType: existingPrice?.priceType ?? 'per_sqft', ← carry forward
    priceDelta: dto.priceDelta.toFixed(2),
    effectiveFrom: now,
    effectiveTo: null,
  }).returning();

BUG-06 — Estimate Number Collision Crashes DB at ~1,100 Estimates
--------------------------------------------------------------------------------
Severity : CRITICAL
File     : backend/src/modules/calculator/calculator.service.ts
           (generateEstimateNumber function)
Impact   : After ~1,100 estimates per year, ~50% of new estimate creation
           requests fail with a PostgreSQL UNIQUE constraint violation.
           Error is unhandled → 500 response to customer. Service degrades.

ROOT CAUSE
The function generates a random 6-digit number from a pool of 900,000 values.
By the birthday paradox, collision probability hits 50% at ~1,116 estimates.
The estimates.estimateNumber column has a UNIQUE constraint.
There is no retry or collision detection logic.

BROKEN CODE:
  export function generateEstimateNumber(): string {
    const year = new Date().getFullYear();
    const randomNum = Math.floor(100000 + Math.random() * 900000);
    return `EST-${year}-${randomNum}`;
    // No collision handling at all
  }

FIX — Option A: Use crypto for 4 billion range:
  import { randomBytes } from 'crypto';
  export function generateEstimateNumber(): string {
    const year = new Date().getFullYear();
    const hex = randomBytes(4).toString('hex').toUpperCase();
    return `EST-${year}-${hex}`;
  }

FIX — Option B: Add retry loop in calculateEstimate():
  let estimateNumber = generateEstimateNumber();
  for (let i = 0; i < 5; i++) {
    const exists = await db.query.estimates.findFirst({
      where: eq(estimates.estimateNumber, estimateNumber)
    });
    if (!exists) break;
    estimateNumber = generateEstimateNumber();
  }

BUG-07 — CORS Whitelist Is Dead Code — All Origins Allowed
--------------------------------------------------------------------------------
Severity : CRITICAL
File     : backend/src/app.ts (CORS origin callback, ~line 18)
Impact   : Any website on the internet can make credentialed cross-origin
           requests to the API in production. Enables CSRF attacks.

ROOT CAUSE
The CORS origin callback has three return branches. The first two handle the
whitelist correctly. But a third "return callback(null, true)" fallback catches
all unmatched origins — making the entire whitelist dead code.

BROKEN CODE:
  origin: (origin, callback) => {
    if (!origin) return callback(null, true);
    if (allowedOrigins.includes(origin) || allowedOrigins.includes('*')) {
      return callback(null, true);
    }
    return callback(null, true); // "Allow dev flexibility"
    // ↑ This line allows EVERY origin. Whitelist does nothing.
  },

FIX (reject unknown origins in production):
  origin: (origin, callback) => {
    if (!origin) return callback(null, true);
    if (allowedOrigins.includes(origin) || allowedOrigins.includes('*')) {
      return callback(null, true);
    }
    if (env.NODE_ENV === 'development') return callback(null, true);
    return callback(new Error(`CORS: origin ${origin} not allowed`));
  },
